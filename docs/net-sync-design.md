# 联机同步设计（2026-11-21 定稿）

> **本文只讲“两台机器怎么看到同一个世界”。** 玩法、数值、经济一律不在这里改。
> 与本文冲突时以本文为准；本文未覆盖的问题回到 `HANDOFF.md` / 模块 `CONTEXT.md`。

## 0. 一句话

**服务器定序，客户端演算。** 服务器用固定定时器推进帧号、绝不等待任何人；客户端只执行“服务器帧号那一帧”的输入，自己的帧号永不超过服务器。

## 1. 边界：哪些是“网络同步”，哪些不是

用户的直觉是对的：传输层相对独立，可以单独推进。但**“完全一致”这个目标有两块地基落在玩法代码里**，不能当成纯网络问题：

| 东西 | 属于 | 说明 |
|---|---|---|
| 帧号推进、帧包收发、补帧、延迟帧 D、重连 | **纯传输层** | 与玩法无关，可独立做、独立验 |
| `state.players`（玩家实体化） | **玩法结构** | 网络正确性的前提：怪物/掉落必须认识“所有玩家”，不能只认识本机 |
| 确定性纪律（禁超越函数/随机/无序遍历） | **玩法编码规范** | 判定位移、命中、掉落的函数必须是确定性函数 |

所以顺序是：传输层可以先做，但**不能只做传输层就宣布“一致”**。

## 2. “一致”的准确定义

必须分两层，否则会得出错误结论：

| | 含义 | 能否保证 |
|---|---|---|
| **tick 状态一致** | 同一帧号上，两端的怪位置/血量、玩家位置/血量、掉落集合、破坏物状态逐字段相同 | **能**（本文的全部内容都在保这一条） |
| 墙钟画面一致 | 同一物理时刻两台屏幕像素相同 | **不能，也不追求** |

做不到第二层的原因：输入要经过 RTT 才生效、客户端还有 D 帧缓冲、各自相机与迷雾不同。**差的是“屏幕上这一刻在显示哪一帧”，不是“哪个世界”。**

## 3. 架构与职责

```
客户端 A ──输入(帧号+帧数据)──┐
                              ├→ 房间进程（造化平台）
客户端 B ──输入(帧号+帧数据)──┘   ① 定时器推进帧号，绝不等客户端
                                  ② 把输入盖到「当前服务器帧号」广播
                                  ③ 记录 hash，发现分叉只留证
                                  ④ 离场宣布（deceased/departed）
                                          │
                        ┌─────────────────┴─────────────────┐
                        ↓                                   ↓
                  客户端 A 按序执行帧                  客户端 B 按序执行帧
                  （本地演算，不做预表现）              （同一份规则、同一份输入）
```

- **服务器不模拟玩法**（可选：留口子，见 §9）。
- **客户端不做预测表现**：收到帧包才推进逻辑，画面不提前。
- 帧包里是**输入**，不是世界状态。

## 4. 帧与时序

### 4.1 帧率：不锁墙钟，跟随服务器

**不要按“24Hz”这种目标值去配定时器。** 实测（两客户端 + 宿主同机）：

| `tickIntervalMs` | 服务端实际 p50 | 客户端观测 p50 | 抖动 p90 |
|---|---|---|---|
| 42 | 46.7 ms | 46.7 ms | 4.1 ms |
| 100 | **109 ms** | 108.9 ms | **1.5 ms** |

- 差值在**服务端**（投递≈0），且不是固定开销：42 差 4.7、100 差 9.0；
- 符合 `实际周期 ≈ 配置值 / (1 − 事件循环负载)`，负载约 8–10%（每 tick 序列化 + 广播）；
- 负载随快照体积变化 ⇒ **偏差会漂，靠配置凑精确帧率是徒劳的**。

**结论**：逻辑帧率 = 服务器实际 tick。客户端只认帧号，不认墙钟。

### 4.2 延迟帧 D：按抖动定，不按 RTT

RTT 高但稳定不需要缓冲（包只是晚到，间隔仍均匀）；用 RTT 调 D 等于让远距离玩家平白多 100ms+。

```
F     = 服务器帧间隔（实测，不假设）
g_i   = 相邻两次「服务器帧号前进」的到达间隔
J     = |g_i − mean(g)| 的 p90（最近 300 帧）
D_raw = ceil(2J / F)
D     = clamp(D_raw + rttBump, 0, 3)
rttBump = (RTT > 150ms 或 RTT > 2×基线) ? 1 : 0
```

变异规则（比公式重要）：

1. **上升立即，下降缓慢**：J 变大马上 +1；连续 3 秒 D_raw 都更低才 -1。
2. **每次只许 ±1，且只在“本地没有待补帧”时调**——否则 D 变化就是画面暂停/快进。
3. D 只影响体验，不影响一致性。

实测基线：本机回环 J=1.5–4.1ms ⇒ **D=1 帧**。真实跨网必须重测，不能沿用。

### 4.3 观感延迟

```
L ≈ RTT + (D+1) · F
```

同城 30ms + D=1 ≈ 110ms；跨省 80ms + D=2 ≈ 200ms。**“不做预表现”意味着这个延迟是裸露的**，没有本地掩饰——这是本方案的已知代价。

## 5. 输入与帧包

1. **客户端上传的帧号仅供参考**，一切以服务器广播的帧号为准。
2. 服务器收到输入后，**盖到当前服务器帧号**广播。
3. **落后丢弃**：`服务器帧号 − 客户端上报帧号 > 24 + D` ⇒ 丢弃本次输入（+D 是因为客户端本来就在后面 D 帧）。24 帧 ≈ 1 秒。
4. **同一时刻收到多帧**：按帧号排序后依次执行，不跳帧、不合并。
5. **缺帧**：立刻向服务器请求补帧；超过 D+3 帧仍未到 ⇒ 冻结画面并提示“重新连接”。
6. **重连静默期**：重连后只收不发，直到 `本地帧号 ≥ 服务器帧号 − D` 才开始上传（否则这段时间的输入会被服务器全部丢弃）。
7. **不踢人**：离线玩家保留座位与实体，对局按倒计时结束 / 全部撤离或死亡才销毁房间。

## 6. 确定性的充分条件（这是“完全一致”的真正来源）

> **不是靠定点数，是靠“只用结果被规范钉死的运算”。**

三条同时成立，即可归纳证明“每帧状态相同”：
状态<sub>N</sub> = f(状态<sub>N−1</sub>, 输入<sub>N</sub>)，f 确定 ⇒ 初值相同 + 输入相同 ⇒ 每帧相同。

1. **判定层只用**：`+ − × ÷`、`Math.sqrt`、`round/floor/ceil/abs/min/max`、整数与位运算。
   这些在 IEEE 754 下是**正确舍入**，跨引擎、跨 CPU 逐位相同。
2. **判定层禁用**（结果没被规范钉死）：
   - `Math.hypot`（规范不要求正确舍入）⇒ 一律改 `Math.sqrt(dx*dx + dy*dy)`
   - `sin/cos/atan2/pow/exp/log` ⇒ 判定用的换 256 项整数查表；纯表现层可保留
   - `Math.random` ⇒ 判定层禁用，表现层可保留但禁止回写状态
   - `Date.now` / `performance.now` ⇒ 逻辑层禁用
3. **结算顺序确定**：遍历用数组下标或按 `playerId` 排序；禁止依赖 `Set/Map` 插入序（插入序 = 网络到达序 = 两端不同）。同一帧多人打同一只怪、同时捡同一件东西，必须按固定顺序结算。

### 6.1 现状清点（2026-11-21）

| 函数 | 处数 | 状态 |
|---|---|---|
| `Math.hypot` | 55 | **已全部替换为 `sqrt`** |
| `sin/cos/atan2/pow` | 53 | 待分类：表现层保留 / 判定层查表 |
| `Math.random` | 6 | 待确认全在 `effects.ts`（表现层） |

### 6.2 守卫

`scripts/check-determinism.mjs` 扫逻辑目录，把 §6.2 的黑名单卡在 CI/`verify.sh` 里。
豁免方式：同行或上一行写 `// determinism-ok: 理由`。

### 6.3 风险边界（什么时候需要回头做定点数）

只要满足以下全部，就不需要定点化：

- 判定层始终跑在 JS 引擎里（V8 / JavaScriptCore / SpiderMonkey 都符合 IEEE 754）；
- 不使用 WASM SIMD 加速模拟；
- 判定逻辑不交给第三方库（它内部顺序不可见）。

**任一被打破，`+ − × ÷` 也不再逐位一致，那时定点化从“白工”变成“必需”。**

## 7. 不变量与验收

| 不变量 | 检查手段 |
|---|---|
| 同帧状态一致 | `hashGameState` 每 60 帧上报，服务端 `stats.mismatches === 0` |
| 玩家状态一致 | hash 按 `id` 排序覆盖**全体**玩家 `x/y/hp`（`f94a6c9` 起）；数组顺序无关 |
| 输入精度一致 | 本机帧与远端帧同走 `toStepInput` 的 1/4 像素量化；单测锁死「直用 vs 往返」逐位相等 |
| 分叉可定位 | `hashGameParts()` 分项（怪 / 掉落 / 玩家 / 破坏物）随 hash 上报，服务端记 `diverged.partsA/partsB` |
| 没有两个世界 | 服务端同 tick hash 全过（`mismatches === 0`）；**墙钟进度偏移**归 §8 第 4 步，见 §10.8 |
| 网络健康 | 角标 `等` 长期为 0，`retx` 不持续增长 |
| 帧流完整 | 服务端 `stats.tickMs` 稳定，客户端 `timing.p90` 不突增 |

**验收口径**：双人跑 3 分钟，上面四个数全过才算“同步成立”。肉眼看画面不算。

**脚本化判据**：`scripts/verify-two-player-net.mjs`（两个真账号 + 造化宿主）14 条硬判据，
`HOLD_MS=180000` 再追加 5 条长跑判据（无分叉 / 两端 tick 差 / tick 仍在涨 / hash 仍在报 /
retx 不持续增长）。判据全是数字，不读截图。**只跑短局会漏掉后期分叉**：14 条判据的
采样窗口约 35 秒，而真实分叉可能从第 720 tick 才开始（见 §10.5），验收必须带 `HOLD_MS`。

> **2026-11-21 的 12/14 假失败**：根因不在同步。`enter()` 用
> `frames().find(f => f.url().includes('serveVersion'))` 抓帧，而宿主外壳的 URL 同样带
> `serveVersion`，抓到外壳时 `login-gate` 为 `null` ⇒ 门禁被误判成 `absent` ⇒ 从没点
> 「继续进入」。`bootIdentity()` 一律 `showGate(false)`，于是门帘全程铺满画布
> （`display:flex / pointer-events:auto / z-index:40`），把所有真实鼠标点击吃掉。脚本点
> 「快速匹配」用的是程序化 `element.click()`，绕过命中测试，所以 12 条网络判据全过，
> 只有「点击驱动走位」两条挂。硬证据是 `engine.localMouse === 0 && localEdges === 0`。
> **排障顺序**：先看 `localMouse / localEdges`（事件有没有进引擎），再看
> `mismatches / diverged`（状态有没有分叉），别靠肉眼猜。
> 探针 `scripts/probe-click-in-host.mjs` 会打印 `gateState`、`elementFromPoint` 命中元素、
> 以及 `frame.click` 被吞掉时的完整 `intercepts pointer events` 报错。

## 9. 明确不做的

- **定点化**：见 §6.3。JS 里收益为零，代价是物理/寻路/命中/掉落全改 + 单测重算。
- **反作弊**：客户端算一切，改内存可作弊。已知洞，不做。
- **客户端预测表现**：本方案刻意不做（延迟换稳定）。若将来要加，只许预测“自己这个玩家的位置”，世界状态永远以服务器为准。
- **不踢人**：离线保留座位（产品决定）。

## 10. 已知未决

1. **服务器 step 的退化口子**：造化平台能给多少 CPU 未知。设计上必须允许“服务端完全不模拟”也能跑（那就没有 checkpoint，重连只能靠输入日志重放）。这决定了重连实现选哪条。
2. **真实网络抖动**：目前只有本机回环数据（J=1.5–4.1ms）。D 公式的参数必须在真实网络上校准。
3. **判定层 `sin/cos` 分类**：守卫预算 47、当前 44 处（`f94a6c9` 实测）。要逐个
   判定“表现 or 判定”，判定用的换成查表；预算只许降。
4. **补帧窗口**：服务端现在只留 24 个 tick 的输入。新设计需要更长（至少覆盖 D+重连静默期），具体值待定。
5. **短局全绿 ≠ 同步成立（已定位并修复，2026-11-21）**：短局 14/14 时
   `divergedTick` 还没出现；`HOLD_MS=180000` 暴露 `divergedTick=600`
   / `mismatches=181`。加 `hashGameParts()` 分项指纹后服务端留下硬证据：
   **怪 / 掉落 / 破坏物三项逐位相同，只有 `players` 不同**
   （`2154890113` vs `1615862512`）。
   根因：`encodeInputFrame` 把 mouse 量化到 1/4 像素，而**本机帧留在本地、
   不过编解码** —— A 用 `1234.567` 的落点走位，B 用解码后的 `1234.5`
   模拟同一个 A，轨迹差 1e-5~0.1px，恰好只让「玩家坐标」分叉。
   修法：`toStepInput()` 对**所有**帧（含本机）统一 1/4 像素量化
   （`Math.round(x*4)/4`，不做 clamp，理由见 §10.9）；
   护栏单测 `assets/net/__tests__/input-frame.test.ts` 先把
   「本机直用 vs 网络往返」的 mouse 差异复现出来再修。
   修复后两端玩家坐标与走位位移**逐位相同**，3 分钟 191 次 hash 零分叉。
   **仍未验**：真实跨网抖动下的 D 参数、弱网补帧窗口、重连静默期。
6. **超时兜底的一致性**：门禁等 300 帧后用空快照开局。若只有一端超时（例如
   一端被遮挡、rAF 被节流），两端初始装备不同 ⇒ 分叉。正常网络下不会触发，
   但这是兜底路径的已知洞；排障看角标的等待帧数。
7. **联机按 R 重开**：`reset()` 只重置 `s.player`（本机），远端玩家的资源不会
   一起重置。两端各自按 R 的行为尚未对齐，属于下一轮。
8. **开局墙钟进度有约 40 帧固定偏移**：两次 3 分钟长跑实测两端 tick 差
   46 / 39 帧，不随时间发散；期间 191 次 hash 零分叉、玩家坐标与走位位移
   逐位相同。偏移来自开局握手（房主先 `startGame`、名单 / 装备快照到达有先后），
   当前没有统一 gate 或追帧机制。这属于 §3 明确**不追求**的「墙钟画面一致」；
   要消除得做 §8 第 4 步的「服务器帧号推进 + 动态 D + 补帧」。验收脚本把它
   作为 `[INFO]` 观测项明示输出，不算进「同帧状态一致」的硬判据。
9. **输入帧坐标上限 8191.75 像素**：`encodeInputFrame` 用 `i16 × 4`，超界的
   世界坐标会被 `clampCoord` 截断。当前联机 arena 坐标在 3000 以内不触发，
   但 worldmap 大地图路点会到 `x=8192` —— 因此 `toStepInput()` **只做 1/4
   像素量化、不做 clamp**（在转换层截断会把 8192 挪到相邻 32px 格、打断
   寻路，verify-all 的 worldmap 实测）。若联机将来也跑大地图，必须扩编码
   （i32 或降精度），否则本机帧与远端帧在超界处仍会分叉。
