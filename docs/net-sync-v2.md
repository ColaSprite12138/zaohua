# 联机同步 v2（2026-11-22 重做）

> **这份文档取代 `net-sync-design.md` 里关于「帧号归属」和「输入归属」的全部内容。**
> v1 文档保留，作为历史结论与踩坑记录；凡是冲突的地方，以本文为准。
> 口径来源：用户 2026-11-22 的 7 条运行原理 + 「服务器存全量帧、补帧不问原因」定稿。

## 0. 为什么重做

v1 的根错误只有一句：

> **客户端为自己的输入保存了一份本地副本，而且没有任何一方有权否决这份副本。**

由此长出全部症状：

| 症状 | 直接原因 |
|---|---|
| 卡 2 秒就永久落后 | 服务器只留 24 帧（1.2 s），历史被裁掉就补不回来 |
| 迟到帧永远丢弃 | `pushRemote` 里 `tick < ls.tick` 直接丢，丢了就没有第二次机会 |
| 全场一起冻 | 执行条件写成「全员输入到齐」，缺一个就谁都别走 |
| 两端 tick 差 40 帧 | 帧号是各端自己数的，没有公共时钟 |
| 卡顿后不能追 | `MAX_STEPS_PER_FRAME = 4` 之后把剩余时间丢掉，宁可慢也不同步 |

v2 的做法是把这两样东西的所有权收到服务器：**帧号归服务器，某帧某玩家按了什么也归服务器。**
客户端不再"拥有"自己的帧，它只是**申报意图**。

## 0.1 三个未知（2026-11-22 已落地，不再阻塞）

落地时**没有**赌这三条的答案，而是绕开了它们：

| # | 未知 | 落地时的处理 |
|---|---|---|
| 1 | 宿主 `getDelta(playerId, ackedSeq)` 是否按玩家定向下发 | **不依赖**。补帧回包按 `reply[playerId] = {seq, …}` 存，客户端只取自己那份；宿主就算全员广播同一份，正确性也不变（只是多花带宽） |
| 2 | 重连进已在 playing 的房间拿到什么 state | **不依赖**。客户端 `nextTick` 从 0 起，缺口一律走 `replay`；重连与抖动同一条通道 |
| 3 | 宿主 `tick()` 能否与逻辑帧率解耦 | **已解耦**。`createGame().start()` 自起 60 Hz 定时器（半周期轮询 + 累加补偿），`tick()` 只让快照「看起来变了」。`scripts/probe-frame-clock.mjs` 实测 58–63 Hz |

## 0.2 落地时踩到的坑：**空帧必须投递**

这是 v2 唯一一个「看起来能跑、其实会永久卡住」的设计陷阱，写在这里当守卫：

客户端是靠「收到第 N 帧」来推进 `nextTick` 的。如果服务器因为「这一帧没人按键」就不把
它放进广播窗口 / 历史，客户端会：

1. 收不到第 N 帧 → `nextTick` 停在 N-1，画面冻住（明明广播一直在来）；
2. 同时看到第 N+5 帧 → 认为中间有洞 → 发 `replay`；
3. `replay` 回来的是「只含有输入的帧」→ 洞还在 → 再要，**永久循环**。

所以：`frame-log.advanceFrame` 允许 `history` 里没有空帧（省内存），
但 **`sliceHistory` 必须按 tick 区间补齐空帧**，且服务器 `onFrame` **每一帧都要写进
广播窗口**（哪怕是空对象）。见 `frame-log.ts::sliceHistory` 与
`game/server/source/index.ts::onFrame` 的注释。


## 1. 权威划分

| 东西 | 所有者 | 客户端能做什么 |
|---|---|---|
| 帧号 / 帧率 | **服务器** | 只读 |
| 第 N 帧里某玩家按了什么 | **服务器** | 只能申报，不能决定自己落在哪一帧 |
| 谁从第几帧起缺席 | **服务器** | 只读 |
| 世界状态 S | 客户端各自演算（确定性保证逐位一致） | 算，但没权改输入归属 |
| 相机 / 迷雾 / HUD / 大地图 | 各端自己 | 随便 |

**由此推出 v2 最刺眼的一条：作者也不能提前用自己的输入。**
我按下 W，它要等这条意图传到服务器、被贴到某一帧、再广播回来，我这一端才执行。
这是「不做预表现」的必然代价，不是 bug。

## 2. 服务器

### 2.1 帧钟

- 帧号用**独立定时器**按 60 Hz（16.67 ms）推进，与广播频率**解耦**。
  **只要时间到就推，不看任何人的脸色** —— 代码里没有任何「还差谁的意图」分支：
  `advanceFrame` 每帧从每人队列取队首一条，取不到就不贴他（= 空输入），
  帧号照走。`scripts/probe-frame-clock.mjs` 有一条硬断言：**零输入 3 秒仍 60.1 Hz**，
  以及「灌 36 条意图不能让帧钟变快」。
  广播每 2–3 帧一批（≈42 ms），一批里带这几帧的全部内容。
  原因：逻辑帧率必须等于帧钟频率。若拿 42 ms 的广播定时器当帧钟，逻辑就变成 24 Hz，
  所有按 dt 的数值、既有基线、单测全要重算。
- 帧号永不等待任何人，也不因某人掉线而变慢。

### 2.2 输入入账

- 上行格式：`{ seq, intents: [...] }`。**意图不带帧号**，只带自己的递增 `seq`（用于去重与诊断）。
- 服务器收到后贴到**当前帧号**。一帧可容纳多个玩家的输入；同一玩家同一帧只保留最先到的那条。
- 不做「落后丢弃」：来晚了就贴到更晚的帧，晚多少就是多少（迟到只影响手感，不影响一致）。

### 2.3 历史与补帧

- `history: Map<tick, Map<playerId, frame>>`，**从第 0 帧留到当前帧，不裁窗口**，房间销毁即释放。
  （3 分钟 2 人 ≈260 KB，16 人 ≈2 MB。）
- `{ replay: { from, to? } }` → 按 **120 帧一块**回发，只给请求者（走 `getDelta(playerId)`）。
  **服务器不关心客户端为什么要补帧**：抖动、断线、重连、换设备，同一条通道。
- 历史**不进**每帧广播的快照（带宽），广播只带新产生的帧。

### 2.4 缺席

- 某玩家连续 `ABSENT_TICKS`（默认 300 帧 = 5 s）没有输入 → 写 `departed(pid, fromTick)`，
  历史从 `fromTick` 起给他写**空帧**。
- 这条只能服务器宣布：各端自行计时会因为起点不同而各自从不同帧开始按空输入算，必然分叉。
- 他回来时走补帧，重放用的历史里那几帧本来就是他"没动"，所以能无缝接上。

### 2.5 对账

- hash 分项指纹照旧收、同帧比对、只留证不裁决。
- 服务器**不**跑 `step()`（除非将来平台剩余算力允许，那也只为 checkpoint，不当真相源）。

## 3. 客户端

只做三件事：**采意图、收帧、执行**。

1. **采样**：每逻辑帧采样一次，打包成「意图」（按键边沿 + 按住 + 指针世界坐标），
   带 `seq`，**不带帧号**。
2. **发送**：每 3 帧一批上行；不重发（重发由补帧通道负责，别两套机制打架）。
3. **接收**：只认服务器广播的帧。执行指针 `nextTick`：
   - 手里有 `nextTick` 这一帧，且领先的**连续帧数 ≥ `lookahead`**（播放缓冲，默认 2）→ 执行并 `nextTick++`；
   - 缺 `nextTick`、但已经看到更高的帧号 → 发 `replay{from: nextTick}`，等块回来依次执行；
   - `nextTick` 永远 ≤ 服务器已广播的最大帧号（天然成立，只执行收到的帧）。
4. **快进**：补帧块到了就连续执行，不渲染中间态（只画最终帧），追上后回到实时。
5. **重连**：只收不发，直到 `nextTick ≥ highestSeen − lookahead` 才开始申报。

`lookahead` 是 v2 里唯一与"手感"有关的旋钮，它的作用和音频抖动缓冲完全一样：
**缓冲几帧，换画面不抖**。它不影响一致性，只影响"卡不卡"和"延迟多少"。

## 4. 代价（必须认下来）

1. **作者延迟增加一个回程**：RTT + lookahead×16.7 ms。本机回环约 40–60 ms，跨网 100–200 ms。
   这是「客户端不做预表现 + 不拥有自己的帧」的必然结果。
2. **服务器必须有 60 Hz 定时器**，不能复用 42 ms 的广播定时器。
3. **断线时画面会停**（因为不预测），恢复靠补帧快进；停多久 = 你多久发现缺口，不再是无限。

## 5. 删除清单（v1 的东西）

| 删掉 | 原因 |
|---|---|
| `lockstep.ts` 的 `localFrames` / `pushLocal` / `localDelay` / 等齐 PEERS | 输入归属改由服务器决定，本地队列没有意义 |
| `InputFrame.tick` → 改 `seq` | 意图不带帧号 |
| `INPUT_WINDOW_TICKS = 24` 与 `lateFrames` 丢弃 | 全量历史 + 补帧通道取代 |
| `MAX_STEPS_PER_FRAME` 后 `acc = 0` 丢时间 | 落后必须补算，不能丢 |
| `runnableTick` 等齐语义 | 改为「等服务器帧」而不是「等所有人」 |

新增：`assets/net/sync-driver.ts`（执行指针 / 缺口 / 播放缓冲，纯逻辑无 DOM）、
服务器侧的 `history` / `replay` / `departed` 超时。

第 2–4 步是**同一批**落地的：协议、服务器、客户端三者是一套，单独改任何一半都会让联机不可用。

### 6.1 第 5 步为什么没做

`scripts/verify-two-player-net.mjs` 需要两个真造化账号（`MATCH_USER_A/B` + 密码）和
detached 宿主，本机没有这两个账号，**跑不了**。所以在拿到账号之前，v2 的正确性证据只到：

- 纯逻辑单测（帧钟语义、补帧区间、执行指针不变式）；
- 服务器**真实产物**探针（`game/server/dist/index.js`，14 项：60 Hz、不等客户端、
  意图按序贴帧、空帧覆盖、replay 分块与 ack）；
- 单机 playthrough（证明客户端主循环改造没破坏单机）。

**还不能说「联机可用」**。第一次拿到双人环境时必须先跑 `HOLD_MS=180000`，重点看：
`netStat.replays` 是否长期为 0、`lead` 是否稳定在 2–4、`gap` 是否长期 0、
服务端 `diverged` 是否为 null。

## 7. 落地后的数据结构（对照用）

| 位置 | 字段 | 含义 |
|---|---|---|
| `game/server/source/index.ts` | `state.frame` | 服务器帧号，60 Hz 自走，**客户端只能跟随** |
| 同上 | `state.inputs[tick][pid] = {t,n:1,b}` | 广播窗口（最近 12 帧，**每帧都有条目**，空对象 = 全员空输入） |
| 同上 | `state.reply[pid] = {seq,from,to,done,more,data}` | 补帧回包，客户端 ack 后删 |
| `assets/net/frame-log.ts` | `history` | 全量历史（只存有人按键的帧，`sliceHistory` 补空帧） |
| `assets/net/sync-driver.ts` | `nextTick` | 执行指针，**结构上不可能超过广播过的帧号** |
| `game.pack.ts` | `intentAcc` / `netOutbox` | 意图采样（墙钟 60 Hz），与执行解耦 |
| 同上 | `MAX_CATCHUP_STEPS = 6` | 每渲染帧最多补 6 步，**剩下的留在 acc 下一帧继续**（不丢时间） |
