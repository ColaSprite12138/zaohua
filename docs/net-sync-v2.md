# 联机同步 v2（2026-11-22 重做）

> **这份文档取代 `net-sync-design.md` 里关于「帧号归属」和「输入归属」的全部内容。**
> v1 文档保留，作为历史结论与踩坑记录；凡是冲突的地方，以本文为准。
> 口径来源：用户 2026-11-22 的 7 条运行原理 + 「服务器存全量帧、补帧不问原因」定稿。

## 0. 为什么重做

v1 的根错误只有一句：

> **客户端为自己的输入保存了一份本地副本，而且没有任何一方有权否决这份副本。**

由此长出全部症状：

| 症状 | 直接原因 |
|---|---|
| 卡 2 秒就永久落后 | 服务器只留 24 帧（1.2 s），历史被裁掉就补不回来 |
| 迟到帧永远丢弃 | `pushRemote` 里 `tick < ls.tick` 直接丢，丢了就没有第二次机会 |
| 全场一起冻 | 执行条件写成「全员输入到齐」，缺一个就谁都别走 |
| 两端 tick 差 40 帧 | 帧号是各端自己数的，没有公共时钟 |
| 卡顿后不能追 | `MAX_STEPS_PER_FRAME = 4` 之后把剩余时间丢掉，宁可慢也不同步 |

v2 的做法是把这两样东西的所有权收到服务器：**帧号归服务器，某帧某玩家按了什么也归服务器。**
客户端不再"拥有"自己的帧，它只是**申报意图**。

## 0.1 三个未知（2026-11-22 已落地，不再阻塞）

落地时**没有**赌这三条的答案，而是绕开了它们：

| # | 未知 | 落地时的处理 |
|---|---|---|
| 1 | 宿主 `getDelta(playerId, ackedSeq)` 是否按玩家定向下发 | **不依赖**。补帧回包按 `reply[playerId] = {seq, …}` 存，客户端只取自己那份；宿主就算全员广播同一份，正确性也不变（只是多花带宽） |
| 2 | 重连进已在 playing 的房间拿到什么 state | **不依赖**。客户端 `nextTick` 从 0 起，缺口一律走 `replay`；重连与抖动同一条通道 |
| 3 | 宿主 `tick()` 能否与逻辑帧率解耦 | **已解耦**。`createGame().start()` 自起 24 Hz 定时器（半周期轮询 + 累加补偿），`tick()` 只让快照「看起来变了」。`scripts/probe-frame-clock.mjs` 实测 23–25 Hz |

## 0.2 「空帧」在两个方向上的规则**不一样**，别搞混

这是 v2 唯一一处「看起来自相矛盾、其实必须分开」的地方。两个方向各有一条铁律：

| 方向 | 规则 | 为什么 |
|---|---|---|
| **上行**（客户端 → 服务器） | 这一帧没有操作就**不发包**，**也不发空帧** | 服务器那一帧里没有他 = 空输入，语义完全等价；而队列是 FIFO 的，前面堆空意图会让真正按下的那一下晚几十帧才生效。判定规则见 `intent-filter.ts`（要覆盖 `pointerHeld` / `pointerOnHud` / `mouse` 这些持续态，不能只判按键） |
| **下行**（服务器 → 客户端） | 每一帧**都必须有条目**（广播窗口里是空对象，历史切片按 tick 补齐） | 客户端靠「收到第 N 帧」推进 `nextTick`。漏掉空帧它就以为那些 tick 还缺 → 画面冻住 + 反复 replay 同一段 → 永久循环 |

也就是说：**上行可以缺、下行不能缺**。上行缺一个玩家，服务器就当他空输入；下行缺一帧，客户端根本不知道那一帧存在过。

落地位置：上行 `game.pack.ts::advanceNet` 里的 `hasActivity` 判断；下行
`game/server/source/index.ts::onFrame`（每帧写 `state.inputs[tick]`）+ `frame-log.ts::sliceHistory`（按区间补齐）。



## 1. 权威划分

| 东西 | 所有者 | 客户端能做什么 |
|---|---|---|
| 帧号 / 帧率 | **服务器** | 只读 |
| 第 N 帧里某玩家按了什么 | **服务器** | 只能申报，不能决定自己落在哪一帧 |
| 谁从第几帧起缺席 | **服务器** | 只读 |
| 世界状态 S | 客户端各自演算（确定性保证逐位一致） | 算，但没权改输入归属 |
| 相机 / 迷雾 / HUD / 大地图 | 各端自己 | 随便 |

**由此推出 v2 最刺眼的一条：作者也不能提前用自己的输入。**
我按下 W，它要等这条意图传到服务器、被贴到某一帧、再广播回来，我这一端才执行。
这是「不做预表现」的必然代价，不是 bug。

## 2. 服务器

### 2.1 帧钟

- 帧号用**独立定时器**按 24 Hz（41.67 ms）推进。
  **只要时间到就推，不看任何人的脸色** —— 代码里没有任何「还差谁的意图」分支：
  `advanceFrame` 每帧从每人队列取队首一条，取不到就不贴他（= 空输入），
  帧号照走。`scripts/probe-frame-clock.mjs` 有一条硬断言：**零输入 3 秒仍 60.1 Hz**，
  以及「灌 36 条意图不能让帧钟变快」。
  **广播频率跟着逻辑帧率走**（`tickIntervalMs = FRAME_MS` = 41.67 ms，2026-11-22 定），
  所以每轮广播正好带 1 帧新内容、窗口只留 4 帧（167 ms，能吸收 3 轮广播丢失）。
  注意两者仍然是**两个不同的定时器**：逻辑帧钟是独立定时器 + 累加补偿，广播是宿主
  的 `tick()`。把它们合成一个会让帧间隔跟着宿主负载抖（见 §8.2）。
- 帧号永不等待任何人，也不因某人掉线而变慢。

### 2.2 输入入账

- 上行格式：`{ seq, intents: [...] }`。**意图不带帧号**，只带自己的递增 `seq`（用于去重与诊断）。
- 服务器收到后贴到**当前帧号**。一帧可容纳多个玩家的输入；同一玩家同一帧只保留最先到的那条。
- 不做「落后丢弃」：来晚了就贴到更晚的帧，晚多少就是多少（迟到只影响手感，不影响一致）。

### 2.3 历史与补帧

- `history: Map<tick, Map<playerId, frame>>`，**从第 0 帧留到当前帧，不裁窗口**，房间销毁即释放。
  （3 分钟 2 人 ≈260 KB，16 人 ≈2 MB。）
- `{ replay: { from, to? } }` → 按 **120 帧一块**回发，只给请求者（走 `getDelta(playerId)`）。
  **服务器不关心客户端为什么要补帧**：抖动、断线、重连、换设备，同一条通道。
- 历史**不进**每帧广播的快照（带宽），广播只带新产生的帧。

### 2.4 缺席

- 某玩家连续 `ABSENT_TICKS`（默认 300 帧 = 5 s）没有输入 → 写 `departed(pid, fromTick)`，
  历史从 `fromTick` 起给他写**空帧**。
- 这条只能服务器宣布：各端自行计时会因为起点不同而各自从不同帧开始按空输入算，必然分叉。
- 他回来时走补帧，重放用的历史里那几帧本来就是他"没动"，所以能无缝接上。

### 2.5 对账

- hash 分项指纹照旧收、同帧比对、只留证不裁决。
- 服务器**不**跑 `step()`（除非将来平台剩余算力允许，那也只为 checkpoint，不当真相源）。

## 3. 客户端

只做三件事：**采意图、收帧、执行**。

1. **采样**：每逻辑帧采样一次，打包成「意图」（按键边沿 + 按住 + 指针世界坐标），
   带 `seq`，**不带帧号**。
   **这一帧没有任何操作就不发、也不发空帧**（`intent-filter.ts`）。判「有没有操作」
   必须覆盖持续态：`pointerHeld` / `pointerOnHud` 为 true 时要一直发（判定层每帧都读，
   少一帧 follow 会掉回 point），`mouse` 变了要发（hover 用当前坐标算）。
2. **发送**：有意图就立刻发（不再攒 3 条 —— 攒批等于让一次点击白等两帧）；
   不重发（重发由补帧通道负责，别两套机制打架）。
3. **接收**：只认服务器广播的帧。执行指针 `nextTick`：
   - 手里有 `nextTick` 这一帧，且领先的**连续帧数 ≥ `lookahead`**（播放缓冲，默认 2）→ 执行并 `nextTick++`；
   - 缺 `nextTick`、但已经看到更高的帧号 → 发 `replay{from: nextTick}`，等块回来依次执行；
   - `nextTick` 永远 ≤ 服务器已广播的最大帧号（天然成立，只执行收到的帧）。
4. **快进**：补帧块到了就连续执行，不渲染中间态（只画最终帧），追上后回到实时。
5. **重连**：只收不发，直到 `nextTick ≥ highestSeen − lookahead` 才开始申报。
6. **执行时：帧里缺席的玩家按「空输入」推进，且本机与远端一视同仁**
   （`net/assemble-inputs.ts::assembleInputs`）。服务器贴定的 `I_all(t)` 是**已定稿的事实**：
   缺一帧由 `sync-driver` 挡在 `step()` 之外，缺席只可能是"他这一帧没操作"。
   所以 `step()` 一旦执行，就要给名单里每个玩家都装上输入（缺席者装空输入），
   绝不 `continue` 跳过整帧。

   > 2026-11-22 真机故障：旧实现只给本机玩家垫空帧（`advanceNet` 的
   > `localFrame ? … : empty`），远端玩家缺席时整帧跳过。于是玩家安静下来之后的
   > 那些帧（站着砸箱、等普攻冷却、走最后几步）**只在自己这一端推进**：
   > A 砸开了箱子、骷髅掉血，B 那边箱子永远砸不开、骷髅不掉血。
   > 回归护栏：`assets/net/__tests__/two-seat-parity.test.ts`（两座位 + 真帧钟）。
   >
   > v1 的「填空输入 = 永久分叉」结论不适用于这里：那一版帧只是**迟到**，
   > v2 里迟到由 `sync-driver` 拦住，根本到不了 `step()`。

   同理，**任何进 hash 的自增序号必须挂在 `S` 上并每局归零**
   （`projectileSeq` / `dropSeq` / `zoneSeq` / `eventSeq`），不能用模块全局计数器：
   两端开局前玩过的局数不同，第一件掉落的 `uid` 就会不同，而 uid 既是 hash 的
   一部分、又是 `pickupTarget` 的匹配键（地面区域 uid、事件刷出的可破坏物 uid
   同样进 hash）。

`lookahead` 是 v2 里唯一与"手感"有关的旋钮，它的作用和音频抖动缓冲完全一样：
**缓冲几帧，换画面不抖**。它不影响一致性，只影响"卡不卡"和"延迟多少"。

## 4. 代价（必须认下来）

1. **作者延迟增加一个回程**：RTT + lookahead×16.7 ms。本机回环约 40–60 ms，跨网 100–200 ms。
   这是「客户端不做预表现 + 不拥有自己的帧」的必然结果。
2. **服务器必须有独立的 24 Hz 定时器**，不能复用宿主的广播定时器（宿主会抖，见 §8.2）。
3. **断线时画面会停**（因为不预测），恢复靠补帧快进；停多久 = 你多久发现缺口，不再是无限。

## 8. 帧率与带宽：为什么逻辑帧率不能跟着广播频率走

### 8.0 先分清两种模式：它们的帧率不一样

| 模式 | 帧率 | 谁定帧号 | 有没有服务器 |
|---|---|---|---|
| **PVE 副本 / 主线**（纯本地） | **24 Hz**（与联机同一套基线） | 客户端自己（墙钟） | 没有。`netActive === false`，`advanceSolo` 走 `advanceClock` |
| **联机 PVP / 联机局** | **24 Hz** | 服务器 | 有。`advanceNet` 只执行广播帧 |

落地方式：步长**不再是全局常量**，而是跟着 `StepClock` 走。

```ts
const stepClock = createStepClock(SOLO_HZ);   // 初始：还没进联机局，跑纯本地
setRate(stepClock, NET_HZ);                   // armTimeline()：进联机局
setRate(stepClock, SOLO_HZ);                  // 回单机 / 新一局 PVE
```

`step(state, stepClock.dt, ...)` 拿到的永远是当前模式那个 `dt`。这不是两套规则集：
玩法数值全是 dt 驱动的（「0.4 秒冷却」就是 0.4 秒），60 Hz 只是把同一秒切成 60 份而不是 24 份。

**为什么单机也降到 24（2026-11-22 用户定，推翻了当天的「单机 60」）**：

只要两种模式帧率不同，任何**按帧**写的判定（「无敌 3 帧」这类）都会变成「单机验过、联机行为不同」，
而验收只在单机跑 —— 这种错只在双人局才暴露。按秒写的判定虽然不受影响（0.36 秒还是 0.36 秒），
但没人能保证以后不写按帧的。

**手感不靠提高逻辑帧率补，靠渲染插值补**（§9）。所以两种模式共用一套帧数语义，
`SOLO_HZ` 现在等于 `NET_HZ`，保留这个名字只是为了「以后想回 60 只改一行」。

证据：`scripts/verify-fixed-step.mjs` —— `state.hz === 24`、实测 **24.2 Hz**，
外加三条插值断言（画面位置与逻辑位置差 **5.75 px**、alpha 有 5 个不同值、偏移不超过一个逻辑步）。

### 8.1 两个频率是**两件事**

| 频率 | 谁定 | 现在 | 能不能改 |
|---|---|---|---|
| 逻辑帧率（联机） | `step-clock.ts::NET_HZ`（唯一真源，`frame-log.ts` 转出） | **24 Hz** | 能，但玩法数值全是 dt 驱动的，改了只是粒度变粗 |
| 逻辑帧率（单机） | `step-clock.ts::SOLO_HZ` | **60 Hz** | 纯本地，不进协议、不参与对账 |
| 广播频率 | `game/server/source/index.ts` 的 `roomPolicy.tickIntervalMs` | **`FRAME_MS` = 41.67 ms（跟着逻辑帧率）** | 能，但宿主负载会跟着涨 |

**一直是 `FRAME_MS` 而不是写死 42**（2026-11-22 用户定）。以前 42 ms 是「少压宿主」的保守值，
代价是每轮攒 2.5 帧、窗口要 12 帧才够抗丢包。现在两者对齐：每轮 1 帧、窗口 4 帧。

### 8.2 为什么不能直接拿宿主 `tick()` 当帧钟

宿主的 `tick()` 是 `setInterval(42)`，实际会落在 42–50 ms（事件循环、序列化开销都在里面）。
若逻辑帧号跟着它走，**帧间隔就不固定** → 画面速度随宿主负载忽快忽慢，
正好违背 §7 的「每帧按时执行」。

所以帧钟必须是**独立定时器 + 累加补偿**（现在的做法）。广播频率跟着逻辑帧率走，
而不是反过来。

### 8.3 带宽实测（`probe-frame-clock.mjs` 第 9 组）

24 Hz 广播（41.67 ms 一轮），实测：

| 场景 | 一次广播 | 带宽 |
|---|---|---|
| 2 人空载（没人按键） | 438 字符 | **10.3 KB/s** |
| 2 人满载（都在动，每帧都发） | ~990 字符 | **~24 KB/s** |
| 16 人满载 | ~5100 字符 | **~120 KB/s** |

对比 60 Hz 那版（25.7 / 58 / 300 KB/s）：降到 24 Hz 让三档都少了 60%，
**这一档收益是实打实的**（与 §8.3 前面「降帧率不省带宽」不矛盾 —— 那里说的是 42 ms→24 Hz
的对比，而把广播从 60 次/秒降到 24 次/秒是另一回事）。

**16 人满载仍偏高，根因是 `playerId`（UUID 36 字符）在每一帧每一人身上重复一遍。**
要再降到 1/3 得做「座位索引」（`inputs` 里用 slot 而不是 id，id 只在 `players` 里出现一次），
这是已知可优化项，不是本轮范围。

**拆开看，74% 是固定开销**：

| 部分 | 占比 | 说明 |
|---|---|---|
| 固定开销 | ~400 字符（2 人空载时占 90%） | `players` / `stats`（19 个数字）/ `stats.tickMs` 分位数 / `departed` / 空 `reply` |
| 输入 | 2 人空载 37 字符；满载每人每帧 ~74 字符 | **每个 playerId（UUID 36 字符）每帧重复一遍** |

**结论：降帧率不是省带宽的主要手段。** 2 人局从 60 Hz 降到 24 Hz 只省下输入那部分的一小半，
而固定开销（`stats` 每轮 218 字符）一分不省。

真正值得做的三件事（按性价比）：

1. **座位索引**（省 2/3 输入）：`inputs` 里用 slot 下标，`playerId` 只在 `players` 里出现一次。
   16 人满载从 ~300 KB/s 降到 ~100 KB/s。
2. **`stats` 低频化**（省一半固定开销）：每 60 轮（1 秒）带一次完整 stats，其余轮给 `{}`。
   2 人空载从 25.7 降到 ~13 KB/s。需要 `meta-ui/net-bridge.js` 缓存上一次非空值。
3. `hashes` 客户端根本不需要收（它只上行），可以从 `getState()` 里剔掉（现在通常是空的，所以省 0）。

### 8.3.1 补帧回包必须带 TTL

补帧回包（一块 120 帧 ≈ 1 KB）在 `state.reply[playerId]` 里，跟着快照每轮广播——
**在 24 Hz 下就是 24 KB/s、60 Hz 下 60 KB/s 的纯浪费**。客户端 ack 后立即删，但如果 ack 丢了或客户端没实现，
它会一直挂着。

所以有 `REPLAY_TTL_TICKS = 180`（宿主 3 秒）兜底：超过就删。
`probe-frame-clock.mjs` 有一条断言专门验这个（不 ack 也会被清掉）。

### 8.4 真要改帧率，动这几处

1. `step-clock.ts::FIXED_HZ`（唯一真源，其余全部由它派生）
2. `roomPolicy.tickIntervalMs` = `FRAME_MS`（跟随逻辑帧率）
3. `RECENT_FRAMES` = 覆盖一轮广播新增帧数 × 4（广播与逻辑同频时每轮 1 帧 → 4）
4. `state-hash.ts::HASH_INTERVAL_TICKS` = `FIXED_HZ`（保持 1 秒一次对账）
5. `step-clock.ts::MAX_CATCHUP_STEPS`（单帧最多补几**步**，现 6）。
   **按步数而不是秒数**，两种帧率下单帧工作量才一致：24 Hz 下 6 步 = 0.25 s、60 Hz 下 = 0.1 s。
   若按秒数写死 0.25 s，60 Hz 下会变成 15 步，切模式后单帧工作量翻 2.5 倍。
6. `net/low-latency.ts::EFFECTIVE_LOOKAHEAD`（帧数 × dt = 固定延迟；当前临时低延迟为 1 帧，24 Hz 时 42 ms；旧模式 2 帧 = 83 ms）
7. 单机 `advanceSolo` 用同一个 `FIXED_DT`，所以**单机手感会一起变**；
   **2026-11-22 定稿：单机 60 Hz、联机 24 Hz，各自取各自的 `dt`**（见 §8.0）。
   改动入口只有 `setRate()` 三个调用点（armTimeline / 回单机 / deploy 单机分支）
8. 重跑：`vitest`、`probe-frame-clock.mjs`（断言里有多处帧数）、单机 playthrough

### 8.5 24 Hz 会不会吃掉判定窗口

最窄的判定窗口是闪避无敌 **0.36 s**（`movement.ts` 里 `p.invuln = 0.36`）。
24 Hz 下是 **8.6 帧**，60 Hz 下是 21.6 帧 —— **判定不会漏**。

真正的代价是**观感**：逻辑位移每 42 ms 才更新一次，60 fps 渲染下会有阶梯感
（200 px/s 的走位 = 每帧跳 8.4 px）。要消掉就得在绘制时用 `acc / FIXED_DT` 做插值。
降到 30 Hz（33 ms）阶梯感减半，带宽与 24 Hz 差不到 1 KB/s（见 §8.3）。

### 8.6 这次对齐带来的两个待实测

1. **宿主能不能接受 `tickIntervalMs = 16.67`。** 若它内部有最小值（clamp 到 20–33 ms），
   广播就会低于 24 Hz，每轮带 1–2 帧。窗口 4 仍然够用，只是延迟略增 —— 不会坏，
   但要在 `stats.tickMs` 里确认 p50 真的是 16–17 ms。
2. **16 人局的宿主 CPU。** `getDelta()` 从 23.8 次/秒涨到 60 次/秒，序列化量 2.5 倍。
   2 人局无压力；16 人局必须实测，扛不住就退回 30 Hz（`FIXED_HZ = 30`，清单见 §8.4）。

这两条都只能在真宿主上验，本机探针回答不了。

### 8.7 客户端到底怎么「跟着服务器帧号走」

用户口径：**收到服务器的帧号事件，就处理事件并推进帧号。** 落地是这样：

```
收到一帧 ──► accept(driver, {tick, frames})   // 只按 tick 塞进缓冲，不动 nextTick
                  │
每渲染帧 ──► while (acc >= FIXED_DT && canStep(driver)) {
                packet = take(driver)        // 取走 nextTick 那一帧
                nextTick += 1                // ← 唯一让帧号前进的地方
                step(state, FIXED_DT, 本机帧, 远端帧)
             }
```

三条必须成立的：

1. **`nextTick` 只在 `take()` 里 +1**，而 `take()` 要求手里从 `nextTick` 起的连续帧数
   ≥ `lookahead`。所以帧号**结构上不可能超过服务器广播过的帧号** —— 不是靠检查拦住的。
2. **不是「收到一帧就立刻执行那一帧」**。那样网络抖动会一比一传进画面：这一帧来得早、
   下一帧晚 60 ms，画面就忽快忽慢 —— 正是 §7 要避免的。`lookahead` 就是那个抖动缓冲：
   手里多攒 `lookahead` 帧再开始播，播放节拍由 `acc`（墙钟）控制，与收包节奏脱钩。
3. **缺帧时不跳、不猜、不填空白**：`canStep` 为 false 就整帧不走、`acc` 不扣时间，
   同时发 `replay` 把洞补上。

旧模式 `lookahead = 2` 在 24 Hz 下 = **83 ms 固定缓冲**。降到 1（42 ms）能省
一半，代价是网络抖动 40 ms 就会让画面停顿 —— 这是延迟与平滑的旋钮，不影响
一致性。2026-11-23 起临时启用 1，见 §8.8。

### 8.8 临时低延迟开关（2026-11-23，可一键回滚）

用户口径：**取消排队缓冲，不取消有序性**。「收到 2800 就执行 2800 的前提是
2799 已收到并执行；2799 的前提是 2798 已收到并执行。没收到 2799 就向服务器
补这一帧。」

`assets/net/low-latency.ts::LOW_LATENCY_NET = true` 时：

| 项 | 旧模式（`false`） | 临时低延迟（`true`） |
|---|---|---|
| `lookahead` | 2（83 ms 抖动缓冲） | **1**（只要 `nextTick` 在手里） |
| 执行节拍 | 墙钟 `acc >= dt`（`takeStep`） | **完全相同，没动** |
| 追帧滞回 | `> 8` 进 / `≤ 3` 出 | **完全相同，没动** |
| 渲染 | 渲染层追随器（§9），与 `acc` 无关 | **与 `lookahead` 无关，没动** |
| 缺帧 | `canStep = false` → `requestReplay` | **完全相同，没动** |

**只有一行生效值变了**：`DEFAULT_LOOKAHEAD = EFFECTIVE_LOOKAHEAD`。省掉
24 Hz 下一帧缓冲（42 ms），角标「领先」从稳定 3 降到 0~1；帧到了最多再等
一个 dt（平均 21 ms），净收益仍是约 42 ms。

#### 8.8.1 为什么不能连「墙钟节拍」一起去掉（2026-11-23 修正）

初版把执行也改成「收到帧就立刻跑」，当天用户实测「移动时整个相机抽搐」，
录屏逐帧测出背景位移 `-1, -6, -2, -1, -5, -1, -4 …` 忽大忽小、夹杂 0 与
反向。根因：

- `paintWithInterp` 连**相机**一起做「渲染落后逻辑一步」插值，`paint()` 用
  `Math.round(s.camera.x)` 整数平移整幅画面；
- 该插值要求执行恰好发生在 `alpha = 1` 的那一刻 —— 墙钟 `takeStep` 的
  `acc >= dt` 保证了这一点：执行前 alpha=1 画 cur，执行后 alpha=0 画
  「新 prev = 旧 cur」，画面无缝；
- 改成收包驱动后，执行落在 alpha=0.2 / 0.9 的任意时刻，每次执行画面突跳
  `(1-alpha)` 个逻辑步，收包间隔又带抖动 → 跳幅忽大忽小 = 相机抽搐。

> 2026-11-23 晚些时候 §9 把玩家/相机换成「渲染层追随器」之后，`alpha = 1` 不再是
> 硬约束（相机不再读 `alpha`）。但**墙钟节拍照样保留**：收包即执行会让一帧内的
> `S` 突增，追随器只能靠 `1.3V` 慢慢追，反而更落后；按 `dt` 稳定执行才能让稳态
> `S` 恒定在一个逻辑步。这一段的历史结论（别去动节拍）仍然有效。

**不是**靠「给相机加指数平滑」解决（那会引入约 60 ms 视觉滞后，把刚省下的
延迟还回来），而是撤销那一步多余的改动：去缓冲只需要 `lookahead 2 → 1`。

**没有取消的东西**：`canStep` 的连续帧检查、`take` 只取 `nextTick`、
`requestReplay` 补洞、每帧完整 `step(dt)`、两端 hash 口径。所以「收到 2800
但缺 2799」时 `contiguous = 0`，一帧都不走，先发 `replay {from: 2799, ...}`；
补齐后才按 2799 → 2800 顺序执行。护栏用例：
`assets/net/__tests__/sync-driver.test.ts`
「低延迟也不越帧：收到 2800 缺 2799 就停住补帧，补齐后按序执行」。

**加回来**：把 `LOW_LATENCY_NET` 改回 `false`，`lookahead` 回到 2，
其余代码一行不用动。

**已知代价**：没有抖动缓冲，网络晚到 40 ms 会偶发顿一下（不是持续抽搐）；
本机输入仍需一个服务器回程（不做客户端预表现），这部分延迟消不掉。
角标「领先」应贴 0~1，若仍稳定 > 3 说明收包/执行链路另有积压。

## 9. 渲染：24 Hz 逻辑怎么做到「不接受跳」

### 9.1 问题

逻辑每 41.7 ms 才更新一次位置。若渲染直接画当前值，60 fps 下一个位置会被画 2~3 帧才跳一次：
205 px/s 走位、24 Hz 逻辑时每步 **8.5 px**，每 41.7 ms 跳一次，肉眼可见。

**这跟网络无关**，纯本地也一样：位置是 `step()` 逐帧算的（`canStand` 碰撞、击退、技能位移全在里面），
不是「A 点到 B 点一次算完」。

### 9.2 做法：渲染层追随器（2026-11-23 起）

`assets/game/visual-motion.ts`。逻辑执行完只交出两个数：**玩家最终位置**、以及这一段逻辑的
**平均速度 `V`**（`路程 ÷ 步数 × dt`，一帧跑 6 步时它仍是 205，不是 1224）。渲染每帧朝目标走：

| 情形 | 判据 | 速度 |
|---|---|---|
| 近区间 | `S ≤ 1 步`（`V·dt`） | **`V`**（严格匀速） |
| 追赶 | `S > 1.5 步` | `min(S / dt, 1.3 V)` |
| 本段无位移 | `V = 0`（顶墙 / 到点 / 被控） | `S / dt`（残差收敛） |

- `S` 是画面位置到逻辑目标的欧氏距离；单帧位移被 `min(speed·dtRender, S)` 夹住，**不过冲**。
- 进入 1.5 步、退出 1 步构成滞回。退出点选 1 步是因为 `S = 一步` 时 `S/dt` 正好等于 `V`，
  切换点速度连续、不可见；1.5 步留出滞回避免阈值附近反复开关。
- `S > 240 px` 判定为不连续位移（传送 / 复活 / 换图 / 出生），直接贴到目标，绝不跨图滑行。
- 到达判据 `S ≤ 0.5 px` 直接贴住，避免浮点渐近永远差一点。

**为什么必须有「近区间」**：只用 `min(S/dt, 1.3V)` 时速度正比于剩余距离，一个逻辑帧只能吃掉
约 63% 的差距，走到下一个逻辑帧边界永远差一截，下一帧再靠 `1.3V` 补回来 —— 表现为
**每 41.7 ms 一次冲-缓（呼吸感）**。死区把稳态钉在 `V` 分支上，速度恒定。这不是调参，
是控制器的稳定性前提（P 控制器的积分项被固定成 1）。

**代价**：画面仍比逻辑晚一步（约 41.7 ms）。知道 `cur` 却不知道 `cur+1`，只能落后；
外推在急停 / 撞墙时会穿墙，不做。稳态行为与旧插值等价，**收益只在补帧**：不再一次快进
多步，而是用 1.3V 平滑拉近。

### 9.3 怎么落地而不改 `paint()`

`paint.ts` 里有 20 多处读 `p.x` / `sk.x` / `s.camera.x`，逐个改成查询既啰嗦又容易漏，
所以用**临时覆盖 + `finally` 还原**（`game.pack.ts::paintWithInterp`）：

```ts
flushVisualTarget();                 // 执行完：把「目标 + 这段逻辑的平均速度」交给追随器
...
paintWithInterp(renderDt, () => paint(painter, state, ...));  // 画前写入视觉位置，画完还原
```

安全性：

- `paint` 是同步的、主循环最后一步，期间没有别的代码读 `S`；
- 判定永远用真实位置（`step()` 已跑完），改的只是绘制那一瞬；
- 新一局 / `setArena` / `reset` 会 `clearPrevPositions()`，它同时置 `visualNeedsSnap`，
  绘制前把追随器硬切到当前坐标（`deploy` 改出生点发生在清理**之后**，所以必须是标记而非立即 reset）。

视觉位置覆盖三类：**玩家、相机、怪**。相机用 `cameraFor(world, 视觉位置)` 重新算，
**必须跟画出去的位置** —— 跟逻辑位置会让玩家离开屏幕中心且偏移逐帧变（2026-11-23 抽搐同类问题）。
掉落 / 弹道 / 区域不处理（它们要么慢、要么本来就该瞬移）。

怪仍按 `alpha = acc/dt` 做「落后一步」插值，它们没有独立追随器。

### 9.4 证据与残留问题

`scripts/verify-visual-smooth.mjs`（`project play`，4 步全绿）：

| 断言 | 实测 |
|---|---|
| 移动中画面速度不超过 1.35×走速 | max **206.1**（走速 205） |
| 稳态中位速度 ≈ 走速 | **205.0** |
| 画面落后不超过 1.8 个逻辑步 | **7.83 px**（一步 8.54） |
| 朝一个方向走时画面不回退 | 0 次回退 |
| 停稳后画面与逻辑位置重合 | ≤ 0.6 px，速度为 0 |

README 里的 `playthrough.mjs`（101 步）同时保持全绿。

**残留问题 1：24 Hz 与 60 Hz 不同步**。一个逻辑帧 = 2.5 个渲染帧，渲染帧边界永远对不齐逻辑边界，
每段会残留 0~3.4 px，由下一段吸收。实测在死区保护下速度仍是恒定 205（因为残留不改变 `S` 的分支），
但在持续抖动 / 补帧后收敛阶段，速度会在 `V ~ 1.3V` 之间过渡。144 Hz（6 帧/步，整除）没有这个现象。

**残留问题 2：绘制仍按 1 px 对齐**。`paint` 里到处是 `Math.round(p.x)`，所以视觉位置到亚像素之后
最小位移单位还是 1 px —— 8.5 px 的跳变成了「每帧 2~3 px 的连续移动」，不是完全无级。
要彻底消除只能放弃像素对齐（画面会糊），这是美术取舍，不在本轮。
